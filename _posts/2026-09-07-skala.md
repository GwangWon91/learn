## 들어가며

SKALA L1 「쿠버네티스 이해 및 앱 배포」 1일차 기록이다. 강의에서는 "왜 쿠버네티스인가"를 시작으로 Pod·매니페스트·라벨·네임스페이스 같은 기본 개념과 클러스터 아키텍처를 훑었고, 실습에서는 AWS CLI 프로필 등록부터 EKS 클러스터 접속, Harbor 레지스트리 로그인, 첫 배포와 `kubectl port-forward`까지를 다뤘다. 개념 정리와 실습 기록을 한 편에 함께 남긴다. 실습은 반 전체가 하나의 네임스페이스를 공유하는 환경에서 진행했기 때문에, 공용 공간에서의 안전 수칙도 함께 정리했다.

## 1. 개념 요약

### 1-1. 왜 쿠버네티스인가

Docker는 컨테이너 하나를 만들고 실행하는 도구이고, Kubernetes는 그 컨테이너들을 여러 개·여러 노드에 걸쳐 운영하는 자동화 도구다. 재시작, 트래픽 분산, 무중단 배포, 롤백, 오토스케일이 여기에 해당한다. 둘은 경쟁 관계가 아니라 함께 쓰는 관계다.

도입 판단 기준은 규모와 배포 빈도다. 필기에 정리된 기준은 두 줄이다.

- 서비스가 한두 개면 EC2에 Docker만 써도 전혀 문제없다.
- 서비스가 5개 이상이고 잦은 배포가 필요할 때 쿠버네티스를 도입한다.

여기에 팀에 아는 사람이 0명이면 PaaS를 먼저 검토하라는 단서가 붙는다. AWS(EC2)는 서버를 빌려주는 것이지 컨테이너 오케스트레이션을 대신해 주지 않으므로, AWS를 쓰더라도 오케스트레이션은 별도로 필요하다. 선택지는 직접 구축(kubeadm), 관리형(EKS), ECS/Fargate 등이다.

| 구분 | kubeadm(직접 구축) | EKS(관리형) |
|---|---|---|
| 컨트롤 플레인 | 서버 3대 이상 직접 구성·감시 | AWS가 다중 AZ로 운영 |
| etcd 백업 | cron으로 직접 | 자동 |
| 인증서 갱신 | 1년마다 수동 | AWS 책임 |
| 사용자가 보는 범위 | 전부 | 노드와 워커 |
| 비용 | — | 클러스터당 시간당 $0.10(월 약 $73) |

> 💡 **인사이트** — AWS를 쓰고 있으니 오케스트레이션도 알아서 되는 것 아닌가 하는 생각이 먼저 들었는데, "서버를 빌려주는 것"과 "컨테이너를 운영해 주는 것"은 다른 층위의 문제였다. EC2 위에서 무엇을 몇 개 띄울지는 여전히 내가 결정해야 한다.

### 1-2. 노드·파드·컨테이너

Pod는 컨테이너 하나 이상을 묶은 최소 배포 단위이며, 컨테이너를 직접 배포하지 않고 Pod로 감싸서 배포한다. 애플리케이션 레벨에서도 최소 단위는 Pod다. 같은 Pod 안의 컨테이너는 네트워크(IP)와 볼륨을 공유하고 생명주기를 같이하지만, 파일시스템(볼륨 제외)과 프로세스는 공유하지 않는다.

| 계층 | IP | 개수 관계 |
|---|---|---|
| 노드(물리·가상 머신, EC2) | VPC 서브넷의 노드 IP | 노드당 최대 58 Pod |
| 파드 | Pod IP 1개, 재생성 시 변경 | 노드 1개 안에 여러 파드 |
| 컨테이너 | Pod IP 공유, localhost로 통신 | 보통 1개, 사이드카 패턴일 때 2~3개 |

Pod 하나에 컨테이너를 여러 개 넣는 것은 일반적인 구성이 아니라 예외다. 로그 수집기처럼 본체를 보조하는 사이드카를 함께 둘 때만 해당한다. 독립적인 앱 두 개를 한 Pod에 넣는 것은 잘못된 설계이며 별도 Deployment로 분리해야 한다.

> 💡 **인사이트** — 처음에는 "노드 안에 파드가 여러 개, 파드 안에 컨테이너가 여러 개"라는 대칭 구조로 이해했다. 앞쪽은 맞지만 뒤쪽은 예외적인 경우라는 정정을 받았다. 계층이 있다고 해서 각 계층이 같은 방식으로 확장되는 것은 아니었다.

### 1-3. 매니페스트와 조정 루프

매니페스트(manifest)는 원하는 상태를 적은 YAML 파일이며, `kubectl apply`로 전달해야 클러스터가 실제로 그 상태를 만든다. 파일만 고치고 apply하지 않으면 클러스터는 바뀌지 않는다. 오브젝트는 원하는 상태인 `spec`과 현재 상태인 `status`로 나뉘고, 컨트롤러가 그 둘의 차이를 좁힌다.

`replicas: 3`을 적고 apply했을 때 일어나는 일은 다음 순서다.

1. YAML이 JSON으로 변환되어 API 서버로 전달된다.
2. etcd에 저장된다.
3. Deployment 컨트롤러가 감지해 ReplicaSet을 생성한다.
4. ReplicaSet 컨트롤러가 현재 개수와 목표를 비교해 부족분만큼 Pod 생성을 요청한다.
5. 스케줄러가 노드를 배정한다.
6. kubelet이 컨테이너를 실행한다.

이 비교와 조정은 한 번으로 끝나지 않고 계속 반복된다. 이것이 조정 루프(reconciliation loop)이며, Pod를 삭제해도 컨트롤러가 다시 채워 넣는 이유다. 멈추려면 `replicas=0`으로 두거나 상위 리소스를 삭제해야 한다.

쿠버네티스는 폴링이 아니라 watch 구조를 쓴다. 변경이 생기면 API 서버가 즉시 알려주기 때문에 반응이 빠르다. `kubectl get pod -w`는 이 watch 메커니즘을 사람 눈으로 직접 구경하는 것이며, 모든 컨트롤러와 kubelet도 같은 방식으로 API 서버를 지켜본다.

#### YAML로 쓰고 JSON으로 읽는다

YAML과 JSON은 서로 다른 데이터가 아니라 같은 데이터를 표현하는 두 가지 문법이다. 사람은 쓰기 좋은 YAML로 매니페스트를 작성하고, kubectl이 이를 JSON으로 변환해 API 서버로 보내며, API 서버는 JSON으로 통신하고 etcd에도 JSON 형태로 저장한다. 조회할 때는 `-o yaml` 또는 `-o json`으로 같은 데이터를 원하는 문법으로 다시 볼 수 있다.

#### dry-run

dry-run은 실제로 저장하지 않고 결과만 미리 확인하는 안전장치다.

| 옵션 | 검증 위치 | 확인 범위 |
|---|---|---|
| `--dry-run=client` | 로컬 | YAML 문법 |
| `--dry-run=server` | 클러스터(저장은 안 함) | admission 정책, 쿼터까지 |

`kubectl create ... --dry-run=client -o yaml`로 매니페스트 뼈대를 자동 생성할 수 있고, `kubectl diff`와 함께 쓰면 적용 전 변경분을 비교할 수 있다.

### 1-4. 라벨과 셀렉터, 그리고 부하분산

쿠버네티스는 이름이 아니라 라벨(label)로 대상을 찾는다. Service는 Pod 이름이 아니라 라벨(selector)로 트래픽을 보낼 대상을 찾기 때문에, Pod 이름이 매번 바뀌어도 연결이 유지된다.

라벨은 Pod IP와 다른 개념이다. 라벨은 사람이 붙이는 key-value 태그(메타데이터)이고, Pod IP는 쿠버네티스가 자동 할당하는 통신 주소다. 라벨은 Pod가 살아 있는 동안 바뀌지 않지만 Pod IP는 재생성마다 바뀐다.

동작은 2단계다.

1. 라벨이 **정확히** 일치하는 Pod만 걸러 Endpoints 목록을 만든다. 대략적인 분류가 아니라 정확한 key-value 매칭이다.
2. 그 목록 안에서 요청마다 무작위로 분산한다.

실제로 오가는 것은 사용자의 HTTP 요청(패킷)이다. Service의 ClusterIP로 도착한 요청을 kube-proxy가 설치한 iptables 규칙이 가로채 Endpoints 중 하나로 전달한다. 필기에 남은 참고 문구대로 Service는 물리적 실체가 없고 각 노드의 iptables 규칙일 뿐이다.

라벨과 애너테이션(annotation)의 차이도 여기서 갈린다. 라벨로는 검색이 되고 애너테이션으로는 되지 않는다. 라벨은 붙이고 덮어쓰고 지우는 대상이고, 애너테이션은 검색이 아닌 기록과 설정에 쓴다.

> 💡 **인사이트** — 처음에는 라벨이 Pod IP를 가리키는 말인 줄 알았고, 이어서 "라벨로 대략 어디로 보낼지 정한 다음 그 안에서 랜덤 분산"으로 정리했다. 방향은 맞았지만 "대략"이 아니라 "정확한 매칭"이라는 점이 핵심이었다. 라벨이 대략적이면 Endpoints 목록 자체를 신뢰할 수 없게 된다.

### 1-5. 핵심 리소스의 전체 그림

여덟 개 리소스가 따로 있는 게 아니라 하나의 요청 경로 위에 순서대로 놓여 있다. 네트워크도 Service 네트워크(클러스터)와 Pod 네트워크(오버레이) 두 겹이다.

![핵심 리소스의 전체 그림](/assets/img/kubernetes-day1/이미지-1.png)
_그림 1. 바깥에서(사용자 → DNS → Load Balancer), 들어오는 문(Ingress, 경로·호스트로 분기), 고정 주소(Service, ClusterIP·부하 분산), 실행 단위(Deployment → ReplicaSet → Pod → Container), 붙는 것들(ConfigMap · Secret · PVC)_

Deployment로 가능한 것은 롤링 업데이트와 무중단 업데이트다. 외부와 정보를 연결하는 것은 Service다. 저장소 쪽은 PV가 공급자, PVC가 소비자 역할이며, PV는 네임스페이스에 종속되지 않고 클러스터 범위에 있다.

> ⚠️ 필기 보완 필요: Service 타입 관련 필기가 "service (node 타입)"에서 끊겨 있어, NodePort를 비롯한 타입별 차이를 확인해 보완해야 한다.

#### 프로토콜 계층에서의 위치

계층 순서는 네트워크(IP, L3) → 전송(TCP, L4) → HTTP(L7)이다. HTTP는 네트워크 바로 다음이 아니라 TCP 연결이 성립된 뒤 그 위에 실리는 내용이다. 이 순서를 알아야 Service와 Ingress의 차이가 설명된다.

| 구성요소 | 계층 | 보는 것 |
|---|---|---|
| CNI(VPC CNI 등) | L3 | Pod IP 할당·라우팅 |
| kube-proxy / Service | L4 | IP:Port만. 내용이 HTTP인지 모른다 |
| Ingress Controller | L7 | HTTP 요청의 경로·호스트를 읽고 분기 |

쿠버네티스 전체는 OSI 계층 하나에 속하지 않는다. 네트워크 프로토콜이 아니라 "컨테이너를 어디에 몇 개 띄우고 관리할지"를 결정하는 오케스트레이션 시스템이며, 인프라 위·애플리케이션 아래의 별도 관리 레이어로 봐야 한다. API 서버·etcd·스케줄러 같은 컨트롤 플레인은 네트워크 계층 개념이 적용되지 않는 순수 제어 영역이다.

컨트롤 플레인은 실제 트래픽 경로에 끼어 있지 않다. 미리 규칙(iptables 등)만 만들어 놓으면 실제 패킷은 커널이 그 규칙에 따라 직접 처리한다. 그래서 API 서버가 멈춰도 이미 실행 중이던 Pod와 그 트래픽은 계속 동작하고, 조회·배포 같은 변경만 되지 않는다. 스케줄러가 멈추면 새 Pod 배치가 Pending 상태가 된다.

"API"라는 말이 두 가지를 가리킬 수 있다는 점도 구분이 필요하다. 쿠버네티스 API 서버(kube-apiserver)는 kubectl·kubelet 등이 호출하는 클러스터 관리 창구이고, 앱의 REST API는 클라이언트가 실제 요청을 보내는 창구다. 클라이언트와 서버를 의미적으로 연결하는 것은 REST API이고, 쿠버네티스(Ingress/Service)는 그 통신이 물리적으로 흐를 경로를 만든다.

> 💡 **인사이트** — 쿠버네티스를 "클라이언트와 서버 사이에서 트래픽을 중계하는 도구"로 이해했다가 정정을 받았다. 쿠버네티스는 사이에 끼어 있는 게 아니라 서버 쪽을 관리하는 도구다. 컨트롤 플레인이 죽어도 트래픽이 흐른다는 사실이 이 구분을 가장 잘 보여준다.

### 1-6. 클러스터와 네임스페이스

쿠버네티스는 오케스트레이션 소프트웨어 자체이고, 클러스터는 그 쿠버네티스가 설치되어 함께 동작하는 노드들의 실제 묶음이다. 같은 쿠버네티스로 여러 개의 클러스터를 각각 운영할 수 있다. 워커 노드는 kubelet, kube-proxy, containerd, pod로 이루어지며 kube-proxy는 에이전트 역할을 한다.

리소스는 네임스페이스 종속 여부로 나뉜다.

| 구분 | 예 | 이름 유일성 |
|---|---|---|
| 네임스페이스 종속 | Pod, Deployment, Service, ConfigMap, Secret, Role | 네임스페이스가 다르면 이름 중복 가능 |
| 클러스터 범위 | Node, PV, StorageClass, ClusterRole | 클러스터 전체에서 유일 |

네임스페이스를 잘 나누는 것이 중요한 이유는 권한 처리 때문이다. 네임스페이스가 없으면 권한을 일일이 처리해야 한다. 롤은 네임스페이스에 종속되고, 클러스터 롤은 전역이라 종속되지 않는다.

EKS에서는 IAM이 인증(authentication)을, RBAC이 인가(authorization)를 담당한다. 그래서 `Unauthorized`와 `forbidden`은 서로 다른 문제다.

#### 실습 클러스터에 설치된 애드온

기본 쿠버네티스에는 없어서 따로 넣어야 하는 것들이 있다. 무엇이 설치되어 있는지 알아야 무엇이 되는지 안다.

| 애드온 | 없으면 | 실습 클러스터 |
|---|---|---|
| CNI (VPC CNI) | Pod가 아예 안 뜬다 | 설치됨(정책 집행은 꺼짐) |
| CoreDNS | 이름으로 통신 불가 | 설치됨 |
| metrics-server | `kubectl top`·HPA 불가 | 설치됨 |
| Ingress Controller | Ingress가 무시된다 | ingress-nginx |
| CSI 드라이버 | PVC가 Pending | EBS · EFS 설치됨 |
| cert-manager | TLS 인증서 수동 | 설치됨(letsencrypt) |
| 로그 수집기 | 로그가 비어 있다 | 없음 |

### 1-7. 컨테이너와 이미지

컨테이너의 정체는 namespace + cgroup + 레이어 파일시스템으로 이루어진 프로세스다. VM이 아니라 커널을 공유한다. 이미지 레이어는 바뀐 줄부터 아래가 다시 빌드되므로 의존성을 소스보다 앞에 두는 순서가 빌드 시간을 좌우한다. 맥 M시리즈는 arm64로 빌드되므로 `--platform linux/amd64`를 습관으로 붙인다.

태그(`myapp:1.0.0`)는 사람이 붙인 이름이라 같은 태그에 다른 내용을 덮어쓸 수 있다. 오늘과 내일 다른 이미지를 받을 수 있다는 뜻이다. 다이제스트(`myapp@sha256:...`)는 이미지 내용으로 계산한 해시이므로 내용이 1비트라도 바뀌면 값이 달라지고, 항상 같은 이미지를 보장한다. `latest`는 배포도 롤백도 못 한다.

다만 실무 해법이 다이제스트 전면 대체는 아니다. 사람이 읽고 기억하려면 태그가 필요하기 때문에, `1.4.2-a3f9c21`처럼 버전에 커밋 SHA를 붙인 불변(immutable) 태그를 쓰고 같은 태그에 재푸시하지 않는 운영 규칙을 지킨다. 완전히 고정해야 하는 베이스 이미지에만 Dockerfile `FROM`에 다이제스트를 쓴다.

> 💡 **인사이트** — 다이제스트가 재현성을 보장한다면 태그는 왜 필요한지, 생성과 수정이 편해서 쓰는 것인지 물었다. 답은 가독성이었다. 기계에게 필요한 식별자와 사람에게 필요한 이름이 다르고, 불변 태그는 그 둘을 한 문자열에서 절충한 결과였다.

### 1-8. IP 대역(CIDR)과 CNI

VPC CIDR(전체 가상 네트워크 범위), 서브넷 CIDR(AZ·용도별로 쪼갠 범위), Service CIDR(ClusterIP용 별도 대역) 등 여러 층의 IP 대역이 있다. `/16`처럼 숫자가 작을수록 넓은 범위다.

EKS는 VPC CNI를 사용해 Pod에 실제 VPC IP를 그대로 할당한다. 일반적인 쿠버네티스가 쓰는 별도 오버레이 대역과 다른 방식이다. 이 때문에 노드가 가질 수 있는 ENI 개수 × ENI당 보조 IP 개수로 계산되는 IP 재고가 노드당 Pod 개수 상한을 만든다. 실습 노드(m6i.xlarge)의 최대 58 Pod도 이 계산 결과다.

### 1-9. kubectl 실무 — 무엇을 알고 싶을 때 무슨 명령인가

강의에서는 목적별로 명령을 대응시켜 정리했다.

| 알고 싶은 것 | 명령 |
|---|---|
| 지금 상태가 어떤가 | `get`, `get -o wide`, `--sort-by` |
| 왜 그런가 | `describe`의 Events |
| 앱이 뭐라고 하나 | `logs`, `logs --previous`, `-c` |
| 값 하나만 뽑고 싶다 | `-o jsonpath`, `custom-columns` |
| 문제 있는 것만 보고 싶다 | `--field-selector=status.phase!=Running` |
| 안에 들어가 보고 싶다 | `exec -it`, `debug`, netshoot |
| 내 노트북에서 붙고 싶다 | `port-forward` |
| 얼마나 쓰고 있나 | `top pods --containers` |
| 적용하면 뭐가 바뀌나 | `diff`, `--dry-run=server` |
| 필드 이름이 뭐였지 | `explain`, `api-resources` |
| 권한이 있나 | `auth can-i` |

막히면 `explain`과 `--v=8`로 확인한다. 클러스터에 직접 물어보는 편이 검색보다 정확하다. 컨테이너 안으로 들어가는 것은 로그로 안 보이는 것을 볼 때인데, 들어가기 전에 `describe`와 `logs`를 먼저 확인한다. `cp`로 파일을 주고받으려면 컨테이너에 `tar`가 있어야 동작한다.

#### port-forward

port-forward는 Ingress 없이도 노트북에서 클러스터 안 서비스에 붙을 수 있는 방법이며, 디버깅 전용이다. 정식 노출 경로(LoadBalancer, Ingress)를 만들지 않고 로컬 포트와 Pod 내부를 임시로 직접 연결하는 개발자용 도구다. 클러스터에 새 리소스를 만들지 않으며 터미널 세션에만 유효하다. 터미널을 닫으면 끊기므로 운영 접근 경로로 쓰지 않는다.

```bash
# Service로 — 뒤 Pod 중 하나로 연결, 부하분산 포함
kubectl port-forward svc/shop-api 8080:80

# Pod로 직접 — 부하분산을 건너뜀
kubectl port-forward pod/shop-api-7d9f8 8080:8080

# 관리 포트만 열어보기
kubectl port-forward deploy/shop-api 8081:8081

# 백그라운드 실행과 종료
kubectl port-forward svc/shop-api 8080:80 &
kill %1
```

특정 Pod 하나만 이상할 때 `pod/`로 직접 붙어 보면 Service 문제인지 해당 Pod 문제인지 바로 갈린다. Pod에 연결이 도달했는데 `connection refused`가 나오면 네트워크 문제가 아니라 컨테이너 안에 해당 포트를 Listen하는 프로세스가 없다는 뜻이다. nginx 환영 페이지가 뜨면 연결 성공으로 본다.

### 2-1. 환경과 전제

| 항목 | 값 |

| 클러스터 | `skala-2026` (Amazon EKS, `ap-northeast-2`) |
| 네임스페이스 | `class-7` — 반 전체가 공유 |
| IAM 사용자 | `skala-class-7` |

kubectl 클라이언트는 클러스터 마이너 버전 기준 ±1 범위 안이어야 안전하다. 이 실습 기준 권장 범위는 v1.35~v1.37이다.

> ⚠️ 필기 보완 필요: 클러스터의 실제 Kubernetes 서버 버전은 `kubectl version --client`로 클라이언트 버전만 확인했고 서버 버전은 직접 조회하지 않았다. 코스맵에는 1.36으로 적혀 있으나 재확인이 필요하다.

### 2-2. AWS 프로필 등록과 EKS 컨텍스트 연결

`aws eks update-kubeconfig`는 클러스터를 새로 만드는 명령이 아니라 로컬 `~/.kube/config`에 접속 설정을 기록하는 명령이다. 접속 순서는 `update-kubeconfig`(설정 생성) → `config set-context --namespace`(기본 네임스페이스 지정) → `use-context`(전환)다.

```bash
# 자격증명 값은 보안상 제외
aws configure set aws_access_key_id <REDACTED> --profile class-7
aws configure set aws_secret_access_key <REDACTED> --profile class-7
aws configure set region ap-northeast-2 --profile class-7
aws configure set output json --profile class-7
```

```bash
aws eks update-kubeconfig --name skala-2026 --region ap-northeast-2 \
  --profile class-7 --alias class-7
# Added new context class-7 to /Users/.../.kube/config

kubectl config set-context class-7 --namespace=class-7
# Context "class-7" modified.

kubectl config use-context class-7
# Switched to context "class-7".
```

클러스터가 여러 개일 수 있으므로 명령을 치기 전 지금 어디를 보고 있는지 확인하는 습관이 필요하다.

```bash
kubectl config current-context
kubectl config get-contexts
# class-7
# CURRENT   NAME      CLUSTER                                                    NAMESPACE
# *         class-7   arn:aws:eks:ap-northeast-2:***:cluster/skala-2026          class-7
```

#### 공유 네임스페이스에서의 삭제 권한 범위

`kubectl auth can-i delete pods` 같은 RBAC 권한은 "본인이 만든 리소스만" 삭제하도록 세분화되어 있지 않고 네임스페이스 단위로 부여된다. 따라서 이름만 정확히 알면 다른 수강생이 만든 Pod도 기술적으로 삭제할 수 있다. 이를 막는 기술적 장치가 없으므로, `delete` 실행 전 반드시 `get pod`로 이름을 눈으로 확인하는 것이 유일한 안전장치다.

> 💡 **인사이트** — 권한 모델이 "네임스페이스 단위"라는 말의 실질적 의미가 여기서 드러났다. 같은 반이 한 공간을 쓰는 이상, 실수를 막는 것은 시스템이 아니라 명명 규칙과 확인 습관뿐이다.

### 2-4. Harbor 레지스트리 로그인

로컬 Docker와 클러스터(kubelet)는 레지스트리 자격증명을 서로 다른 곳에 별도로 보관한다. 로컬은 `docker login` → `~/.docker/config.json`, 클러스터는 `kubectl create secret docker-registry` → Secret(dockerconfigjson)이다. 이 실습 클러스터는 노드가 레지스트리에서 직접 이미지를 받아오도록 구성되어 있어 `imagePullSecrets` 설정이 별도로 필요 없다.

Harbor의 robot 계정 사용자명은 `robot$계정이름` 형식이며, 사람이 로그인하는 일반 계정과 구분되는 자동화 전용 계정이다.

```bash
docker login skala-registry.skala-ai.com -u 'robot$<REDACTED>' -p '<REDACTED>'
# WARNING! Using --password via the CLI is insecure. Use --password-stdin.
# Login Succeeded
```

로그인은 성공했지만 `--password`를 CLI로 넘기는 방식은 경고 대상이며, `--password-stdin`이 권장된다.

### 2-5. 첫 배포와 조정 루프 확인

`kubectl create deployment`는 명령형(imperative) 방식이며, 이 실습에서는 구조를 눈으로 확인하기 위한 목적으로 예외적으로 한 번 사용한다. Deployment는 "복제본이 n개 있어야 한다"는 목표 상태를 계속 감시하는 조정 루프를 실행하므로, Pod 하나를 삭제해도 ReplicaSet 컨트롤러가 즉시 새 Pod를 채워 넣는다. 이때 새로 생기는 Pod는 이름이 다르다. 지워지지 않은 것이 아니라 다시 만들어진 것이기 때문이다.

```bash
kubectl delete pod <hello로_시작하는_실제_Pod_이름>
kubectl get pod
```

### 2-6. port-forward 실습

교재 예시의 이름(`shop-api`)을 그대로 실행하는 것에서 시작해, 실제 리소스 이름을 확인하고 대조군을 만들어 확인하는 순서로 진행했다.

```bash
kubectl port-forward deploy/shop-api 8080:8080
# Error from server (NotFound): deployments.apps "shop-api" not found

kubectl get deploy
# NAME               READY   UP-TO-DATE   AVAILABLE   AGE
# attach-my-deploy   1/1     1            1           34d
# kubectl-deploy     1/1     1            1           34d
```

존재하는 Deployment로 다시 시도했다.

```bash
kubectl port-forward deploy/kubectl-deploy 8080:8080
# Forwarding from 127.0.0.1:8080 -> 8080
# Forwarding from [::1]:8080 -> 8080
# Handling connection for 8080
# E0907 15:23:42.178143 portforward.go:522] "Unhandled Error"
#   err="... dial tcp4 127.0.0.1:8080: connect: connection refused ..."
# error: lost connection to pod
```

컨테이너 내부에서 Listen 포트를 확인하려 했으나 이미지에 `ss`가 없었다.

```bash
kubectl exec deploy/kubectl-deploy -- ss -ltnp
# error: Internal error occurred: ... exec: "ss": executable file not found in $PATH
```

port-forward 기능 자체가 정상인지 확인하기 위해 nginx 이미지로 별도 Deployment를 만들어 대조군으로 삼았다.

```bash
kubectl create deployment test-p239 --image=nginx --dry-run=client -o yaml > test.yaml
kubectl apply -f test.yaml
# deployment.apps/test-p239 unchanged

kubectl port-forward deploy/test-p239 8080:80
# 브라우저에서 nginx 기본 환영 페이지 확인
```

이 대조군이 성공했다는 것은 port-forward 기능·네트워크·클러스터 상태 자체가 정상이라는 뜻이다. 응답 화면의 내용 자체는 의미가 없고, 끝까지 연결되어 응답이 왔다는 사실만 중요하다. 이로써 문제 범위는 도구가 아니라 특정 앱(대상 컨테이너)의 설정·상태로 좁혀졌다.

> 💡 **인사이트** — nginx 환영 페이지가 뜨는 것이 왜 중요한지 처음에는 이해하지 못했다. 화면의 내용이 아니라 "연결이 끝까지 도달했다"는 사실이 증거였다. 디버깅에서 대조군을 하나 세워 두면 원인 후보를 절반으로 줄일 수 있다는 것을 실제로 확인한 지점이다.

이어서 교재의 Service·Pod 예시도 그대로 실행해 봤다.

```bash
kubectl port-forward svc/shop-api 8080:80
# Error from server (NotFound): services "shop-api" not found

kubectl get svc
# No resources found in class-7 namespace.

kubectl port-forward pod/shop-api-7d9f8 8080:8080
# Error from server (NotFound): pods "shop-api-7d9f8" not found

kubectl get pod
# NAME                               READY   STATUS    RESTARTS   AGE
# attach-my-deploy-8548999c9-bl5kx   1/1     Running   0          17h
# kubectl-deploy-558859bb69-wsnpc    1/1     Running   0          17h
# test-p239-5b4947f658-tdk6k         1/1     Running   0          5m43s
```

`shop-api-7d9f8` 같은 이름은 설명을 위한 예시이며 실제 존재하는 Pod 이름이 아니다. Pod 이름은 `Deployment이름-랜덤해시-랜덤해시` 형식으로 쿠버네티스가 자동 생성하므로, 실제 이름은 매번 `kubectl get pod`로 확인해야 한다.

### 트러블슈팅

#### 자격증명 프로필 누락 — `NoCredentials`

`aws configure set ... --profile <이름>`으로 프로필별 자격증명을 등록하면 이후 명령에도 반드시 같은 `--profile`을 지정해야 한다. 생략하면 AWS CLI는 `default` 프로필을 참조하는데 거기에는 자격증명이 없다.

```bash
aws sts get-caller-identity
# NoCredentials: Unable to locate credentials

aws sts get-caller-identity --profile class-7
# {
#     "UserId": "AIDA...",
#     "Account": "***",
#     "Arn": "arn:aws:iam::***:user/skala-class-7"
# }
```

#### 리소스 이름의 대문자 — RFC 1123

```bash
kubectl create deployment test-P239 --image=nginx --dry-run=client -o yaml > test.yaml
kubectl apply -f test.yaml
# The Deployment "test-P239" is invalid: metadata.name: Invalid value: "test-P239":
# a lowercase RFC 1123 subdomain must consist of lower case alphanumeric characters,
# '-' or '.', and must start and end with an alphanumeric character
```

원인은 이름에 포함된 대문자(`P239`)다. 쿠버네티스 오브젝트 이름은 소문자·숫자·하이픈·점만 허용하고 시작과 끝은 영숫자여야 한다(RFC 1123 subdomain). 리소스 이름이 DNS 이름이나 라벨 값으로도 쓰이기 때문에 대소문자 구분 문제를 없애려 소문자로 강제한 것이다. 개인 식별자를 붙일 때도 `P000`이 아니라 `p000`처럼 소문자로 통일해야 한다.

소문자로 바꿔 재적용하자 `deployment.apps/test-p239 unchanged`가 출력됐다. 이는 에러가 아니라 "이미 목표 상태와 같아 바꿀 게 없다"는 뜻이며, 선언형 apply의 멱등성을 보여준다.

#### 자리표시자를 그대로 입력해 발생한 셸 파싱 오류

안내문에서 `<pod-name>`처럼 꺾쇠괄호로 감싼 부분은 "실제 값으로 바꿔 넣으라"는 표시일 뿐 명령어 문법의 일부가 아니다. 이를 그대로 셸에 입력하면 zsh/bash가 `<`, `>`를 파일 리다이렉션 기호로 해석한다.

```bash
kubectl delete pod <pod/hello-54995c79cf-5w29p>
# zsh: parse error near '\n'
```

#### `connection refused` — 미해결

`kubectl-deploy`에 대한 port-forward에서 발생한 `connection refused`는 원인 후보로 (1) 앱이 8080이 아닌 다른 포트 사용, (2) 앱이 아직 완전히 기동되지 않음, (3) 기동 중 크래시를 검토했다. `kubectl exec ... ss -ltnp`는 이미지 내 도구 부재로 실패했고, `kubectl logs`와 `kubectl debug --image=nicolaka/netshoot`를 통한 추가 확인은 진행하지 않아 실제 원인은 확인되지 않은 상태다.

#### 개인 식별자 확인 실패

`kubectl get all -n class-7 --show-labels`로 다른 수강생 리소스의 네이밍 패턴을 유추하려 했으나, 기존 리소스가 33일 전 생성된 데모용이라 식별자 패턴 자체가 없어 유추에 실패했다. 이 값은 명령으로 조회할 수 없으므로 강사에게 직접 확인하는 방법밖에 없다.

## 3. 심화: 남은 질문과 사고 확장

### Q. AWS 액세스 키를 채팅에 붙여넣어도 되는가

되지 않는다. 실습 초반에 액세스 키와 시크릿 키를 그대로 붙여넣었고, 지적을 받은 이후로는 자격증명이 필요한 모든 명령에서 값을 가린 형태로 질문하는 방식으로 바꿨다. 해당 키는 IAM 콘솔에서 비활성화하고 새로 발급받아 재등록하는 조치가 필요하지만, 실제 재발급 여부는 아직 확인하지 못했다.

반면 `aws sts get-caller-identity`의 출력에는 Account·UserId·Arn만 있고 액세스 키·시크릿 키 같은 자격증명 값 자체는 포함되지 않는다. 둘은 구분해서 다뤄야 한다.

### Q. 같은 네임스페이스를 쓰는 다른 사람의 Pod도 지울 수 있는가

기술적으로 가능하다. RBAC 권한이 리소스 소유자별로 나뉘어 있지 않고 네임스페이스 단위로 부여되기 때문이다. 이름 확인이 유일한 예방책이다.

### Q. `kubectl-deploy` Pod는 실제로 어느 포트를 Listen하고 있는가

아직 확인하지 못했다. `kubectl get pod ... -o jsonpath='{.spec.containers[0].ports[*].containerPort}'`로 실제 컨테이너 포트를 조회한 뒤 port-forward를 재시도하면 확인할 수 있을 것으로 보이나, 대화 시점에는 진행하지 못했다.

### Q. `svc/` 대상 port-forward는 어떻게 실습하는가

`kubectl get svc` 결과가 비어 있어 Service 자체가 없었다. `kubectl expose deployment ... --name=...`으로 Service를 직접 만들어야 하는데, 이 시도는 아직 하지 못했다.

### Q. 자리표시자를 제거한 뒤 `kubectl delete pod`가 실제로 성공했는가

아직 확인하지 못했다. 조정 루프로 새 Pod가 다른 이름으로 생성되는 것을 직접 관찰하는 단계까지 가지 못했다.

### Q. "get call"은 무슨 명령인가

아직 확인하지 못했다. HTTP GET인지, `kubectl get`의 오기인지, 다른 도구의 용어인지 특정하지 못한 채 남았다.

### Q. 개인 식별자(P000)의 실제 배정 번호는 무엇인가

아직 확인하지 못했다. 강사 확인 대기 중이다.

## 📌 회고

1일차의 절반은 개념이었고 절반은 "예시와 실제를 구분하는 훈련"이었다. `shop-api`, `shop-api-7d9f8`, `<pod-name>` 세 가지 모두 교재나 안내문의 표기일 뿐인데 그대로 실행해서 세 번 에러를 냈다. 세 번 모두 해법은 같았다. 내 클러스터에 실제로 무엇이 있는지 `get`으로 먼저 조회하는 것이다.

개념 쪽에서는 스스로 정리한 이해를 검증받는 과정에서 정정이 여러 번 있었다. 라벨 매칭이 "대략"이 아니라 "정확히"라는 점, 쿠버네티스가 클라이언트와 서버 "사이"가 아니라 "서버 쪽"을 관리한다는 점, Pod 안 컨테이너 여러 개는 일반이 아니라 예외라는 점이 그것이다. 틀린 방향이 아니라 미세하게 어긋난 이해였기 때문에, 스스로 정리해서 확인받지 않았으면 그대로 넘어갔을 것들이다.

가장 반성할 지점은 자격증명을 그대로 붙여넣은 일이다. 이후로는 값을 가리고 질문하도록 습관을 바꿨지만, 유출된 키의 재발급은 아직 처리하지 못했다. 다음 실습 전에 액세스 키 재발급과 개인 식별자 확인을 먼저 끝내고, `kubectl-deploy`의 Listen 포트 확인과 `test-p239` 임시 리소스 정리를 이어서 진행한다.
